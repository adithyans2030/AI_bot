Binary Search Trees — Extended Unit Notes. A binary search tree (BST) is a binary tree where every node's left subtree contains only keys smaller than the node's own key, and every node's right subtree contains only keys larger than it. This ordering property holds recursively at every single node in the tree, not just at the root, which is what makes the whole structure searchable in the first place. Because the ordering is consistent throughout, at every node you can decide which subtree to descend into with a single comparison, without ever needing to inspect the subtree you didn't choose. This one property is the foundation that every other operation on a BST leans on: search, insertion, deletion, and traversal all depend on the same left-smaller, right-larger guarantee to know where to look for an existing key or where to place a new one. Unlike a plain sorted array, a BST supports insertion and deletion without shifting large blocks of existing elements, which is the whole reason the tree shape is worth the extra pointer overhead compared to a flat array representation. The height of the tree — the length of the longest path from root to leaf — directly determines how expensive every operation is, since every operation is fundamentally a root-to-somewhere walk bounded by that height.

In-order traversal visits a BST's nodes in a fixed order: first the entire left subtree, then the current node itself, then the entire right subtree, applied recursively at every level of the tree until every node has been visited exactly once. Because of the BST ordering property described above, this specific traversal order always produces the tree's keys in fully sorted ascending order, with no separate sorting pass required afterward. This is a genuinely useful way to sanity-check that a tree actually satisfies the BST property after a long sequence of insertions and deletions, since if the in-order output ever comes out unsorted, something has violated the ordering invariant somewhere in the tree. Pre-order traversal (node, then left, then right) and post-order traversal (left, then right, then node) are the two other standard traversal orders, and they matter for different tasks: pre-order is the natural order for reconstructing a tree from scratch or serializing it to a file, while post-order is the natural order for safely deleting an entire tree node by node, since a node's children are always processed and freed before the node itself.

Searching for a key in a BST starts at the root and compares the target key against the current node's stored key. If the two match, the search is done and the node has been found. If the target is smaller than the current node's key, the search continues into the left subtree; if the target is larger, it continues into the right subtree; this process repeats at each new node until either a match is found or a null pointer is reached, which means the key is not present anywhere in the tree. In a reasonably balanced tree, each comparison along this path eliminates roughly half of the remaining candidate nodes from consideration, which gives search an expected running time of O(log n) — the same logarithmic behavior you get from binary search over a sorted array, and for essentially the same underlying reason. In a badly unbalanced or degenerate tree, however, this guarantee completely breaks down and search can degrade all the way to O(n), which is precisely why keeping a tree balanced matters so much for real-world performance rather than just being a theoretical concern.

Insertion into a BST follows the exact same downward comparison path that search does: starting at the root, repeatedly comparing the new key against the current node and moving left or right accordingly, until a null pointer is reached at the bottom of some path. The new key is then attached there as a brand-new leaf node, and nothing else about the tree's existing structure needs to change. Insertion never needs to rearrange or move any of the tree's other nodes in a plain, unbalanced BST — it only ever adds exactly one new leaf at the end of whatever comparison path the new key's value dictates. This is part of why insertion is cheap on average: it costs exactly one root-to-leaf walk plus the creation of a single new node, and every other node in the tree is left completely untouched by the operation.

Deletion is the operation most students find confusing, because unlike search and insertion it splits into three genuinely distinct cases depending on how many children the node being removed actually has. If the node being deleted is a leaf with no children at all, it can simply be removed outright with no further bookkeeping required. If the node has exactly one child, that single child is spliced directly up into the deleted node's old position, which automatically preserves the BST ordering property without any extra work. If the node has two children, the standard technique is to find its in-order successor — defined as the smallest key in its right subtree, found by moving right exactly once and then left as far as possible from there — copy that successor's key value into the node being deleted, and then delete the successor node instead of the original target. The successor found this way is always guaranteed to have at most one child of its own, so that second, substitute deletion always falls back into one of the two simpler cases already described above, never back into this same two-child case again.

Left unmanaged, a plain BST's real-world performance depends entirely on the order its keys happen to be inserted in, which is a serious practical weakness. If keys arrive already sorted, or nearly sorted, every new node ends up becoming a right child of the previous one (or every one a left child), and the tree degenerates into what is functionally a linked list, with search, insertion, and deletion all falling to O(n) instead of the O(log n) a balanced tree would give. Self-balancing variants exist specifically to prevent this degeneration from ever happening. AVL trees track a strict height-balance factor at every single node and perform local rotations after every insertion and deletion to keep the tree's overall height within a tight logarithmic bound at all times. Red-black trees instead use a node-coloring scheme with looser balance constraints that require fewer rotations on average to maintain, at the cost of allowing a slightly taller worst-case tree than a strict AVL tree would ever permit. Both of these self-balancing schemes guarantee O(log n) height no matter what order the keys were originally inserted in, which is exactly the guarantee a plain unbalanced BST cannot offer.

Balanced binary search trees and their close relatives show up constantly in real production systems, not just in textbook exercises. Database indexes and filesystem directory structures very commonly use B-trees, which are a wider generalization of the same left-smaller-right-larger ordering idea, specifically adapted so that each node holds many keys sized to match a disk block instead of holding just one key per node. In-memory ordered maps and ordered sets in many standard programming-language libraries are implemented internally as red-black trees, specifically because those data types need a guaranteed logarithmic bound on lookup, insertion, and deletion, together with the ability to walk all the keys back out in sorted order cheaply via in-order traversal whenever that's needed. Compared to a hash table, a balanced BST trades away a small amount of raw average-case lookup speed in exchange for the ability to answer range queries and produce sorted output efficiently — which is exactly why a BST-based structure gets chosen over a hash table whenever sorted iteration or range queries actually matter to the application.
